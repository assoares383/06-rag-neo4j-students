# RAG Neo4j Students Project Specification

## 1. Purpose of This Document

This document describes the purpose, architecture, data model, execution flow, integration contracts, and evolutionary roadmap of the `rag-neo4j-students` project.

It was written to serve as both a learning resource and a reference for future implementations. Therefore, it distinguishes between:

- **Current State**: behavior and structure found in the codebase.
- **Target Architecture**: behavior the project intends to provide once the currently incomplete nodes have been implemented.

This distinction is necessary because the `README.md` still documents an article generator, while the current implementation is transitioning to a sales analytics assistant.

## 2. Overview

The project is an API for answering questions about educational and commercial data. Users can ask questions such as:

- Which courses are available?
- Who purchased a specific course?
- What was the revenue generated by credit card payments?
- Which students have reached 100% course completion?
- Which courses are frequently purchased together?

The system must transform the question into a **Cypher** query, execute it against Neo4j, and convert the results into an understandable analytical response.

The conceptual workflow is:

```text
Natural Language Question
        |
        v
Question Extraction
        |
        v
Complexity Analysis
        |
        v
Cypher Generation by the LLM
        |
        v
Validation and Execution in Neo4j
        |
        +--> Query Correction, if necessary
        |
        v
Natural Language Analytical Response
```

Although the project name contains "RAG", the current implementation does not include vector search or embeddings. The implemented mechanism is primarily **Graph QA**: retrieving structured data from Neo4j through a query generated by a language model.

## 3. Learning Objectives

This project can be used to study:

1. Building APIs with Fastify and TypeScript.
2. Modeling relational data in a graph database.
3. Writing Cypher queries.
4. Translating natural language into database queries.
5. Orchestrating agents with LangGraph.
6. Using structured outputs with Zod.
7. Validating and automatically correcting LLM-generated queries.
8. Breaking down complex questions into multiple steps.
9. End-to-end testing involving LLMs, Neo4j, and HTTP.
10. Observability, security, and cost management in AI applications.

## 4. Functional Scope

### 4.1 Planned Features

- Receive questions through HTTP.
- Identify the most recent question submitted by the user.
- Classify questions as simple or complex.
- Break complex questions into up to three subquestions.
- Generate Cypher queries compatible with the actual Neo4j schema.
- Validate queries using `EXPLAIN`.
- Execute queries with parameters whenever applicable.
- Attempt to correct an invalid query once.
- Generate responses containing data, calculations, and comparisons.
- Suggest follow-up questions.
- Report errors in an understandable way.

### 4.2 Currently Out of Scope

- Modifying data through user questions.
- User authentication and authorization.
- Visual dashboards.
- Model training or fine-tuning.
- Vector indexing of documents.
- Conversation history persistence.
- Guaranteeing that randomly generated data represents real business data.

## 6. Current Technical Architecture

### 6.1 API

The application uses Fastify. The server is created by `createServer()` in `src/server.ts` and listens on port `4000` when started through `src/index.ts`.

The current endpoint is:

```http
POST /sales
Content-Type: application/json
```

Request body:

```json
{
  "question": "List all available courses"
}
```

Target response:

```json
{
  "answer": "There are 10 available courses...",
  "followUpQuestions": [
    "Which courses generate the most revenue?",
    "Which students completed their courses?"
  ],
  "query": "MATCH (c:Course) RETURN c.name AS courseName",
  "error": null
}
```

The `query` field is useful for learning and debugging, but it should be hidden in public environments if it exposes internal database details.

### 6.2 LangGraph

The main state is defined in `src/graph/graph.ts` and includes:

| Field | Type | Purpose |
|---|---|---|
| `messages` | `BaseMessage[]` | Input and output messages |
| `question` | Optional `string` | Extracted question |
| `query` | Optional `string` | Current Cypher query |
| `originalQuery` | Optional `string` | Query before corrections |
| `dbResults` | Optional `any[]` | Neo4j results |
| `correctionAttempts` | Optional `number` | Number of correction attempts |
| `validationError` | Optional `string` | Validation error |
| `needsCorrection` | Optional `boolean` | Indicates a correctable failure |
| `isMultiStep` | Optional `boolean` | Indicates decomposition |
| `subQuestions` | Optional `string[]` | Subquestions |
| `currentStep` | Optional `number` | Current step |
| `subQueries` | Optional `string[]` | Queries generated for substeps |
| `subResults` | Optional `any[][]` | Results from substeps |
| `answer` | Optional `string` | Final answer |
| `followUpQuestions` | Optional `string[]` | Suggested follow-up questions |
| `error` | Optional `string` | Functional error |

Current topology:

```text
START
  -> extractQuestion
  -> queryPlanner
  -> cypherGenerator
  -> cypherExecutor
  -> [cypherCorrection] (conditional)
  -> analyticalResponse
  -> END
```

The `queryPlanner` uses a structured output defined in `src/prompts/v1/queryAnalyzer.ts`. The classification supports up to three subquestions, but full support for multi-step processing has not yet been completed.

### 6.3 Services

`Neo4jService` encapsulates:

- Lazy initialization of `Neo4jGraph`.
- Schema retrieval.
- Validation using `EXPLAIN`.
- Query execution.
- Database cleanup.
- Connection shutdown.

`OpenRouterService` encapsulates a `ChatOpenAI` instance configured to use OpenRouter's OpenAI-compatible API. It provides structured generation using an agent and `toolStrategy`.

## 7. Neo4j Data Model

### 7.1 Nodes

#### `Course`

| Property | Type | Description |
|---|---|---|
| `name` | string | Unique name used by the seed process |
| `url` | string | Public course URL |

#### `Student`

| Property | Type | Description |
|---|---|---|
| `id` | string | Student UUID |
| `name` | string | Full name |
| `email` | string | Email address |
| `phone` | string | Phone number |

### 7.2 `PURCHASED` Relationship

```text
(Student)-[PURCHASED]->(Course)
```

Properties:

| Property | Type | Description |
|---|---|---|
| `status` | `paid` or `refunded` | Purchase status |
| `paymentMethod` | `pix` or `credit_card` | Payment method |
| `paymentDate` | ISO string | Transaction date |
| `amount` | number | Purchase amount |

### 7.3 `PROGRESS` Relationship

```text
(Student)-[PROGRESS]->(Course)
```

Property:

| Property | Type | Description |
|---|---|---|
| `progress` | Integer from 0 to 100 | Completion percentage |

The seed process creates progress records only for purchases with a `paid` status. Therefore, the question "Which students have progress records without a purchase?" should normally return zero results with the data generated by the seed process. This is useful as an edge case, but it does not necessarily represent an inconsistency that can occur in this generator.

## 8. Data Seeding Process

The `npm run seed` command:

1. Clears the database using `MATCH (n) DETACH DELETE n`.
2. Generates 20 students.
3. Generates between 1 and 10 purchases per student.
4. Randomly selects courses from `courses.json`.
5. Assigns purchase status, payment method, date, and amount.
6. Creates progress records for paid purchases.
7. Inserts the data using `UNWIND` and parameters.

Since the data is randomly generated, tests that depend on specific names, values, or exact quantities may be unstable. Integration tests should validate invariants, such as response format, field existence, and consistency between results, or use a dedicated fixed dataset for testing.

## 9. LLM Prompts and Contracts

### 9.1 Complexity Analysis

`QueryAnalysisSchema` requires:

```json
{
  "complexity": "simple",
  "requiresDecomposition": false,
  "subQuestions": [],
  "reasoning": "Direct retrieval"
}
```

### 9.2 Cypher Generation

The prompt in `cypherGenerator.ts` instructs the model to:

- Use explicit aliases.
- Return flat fields.
- Prefer `elementId()` over `id()`.
- Use `CASE` for conditional counts.
- Use `EXISTS { ... }` for existence checks.
- Apply filters early.
- Limit relationship traversal depth.
- Return Cypher only, without Markdown code blocks.

### 9.3 Query Correction

`CypherCorrectionSchema` requires:

```json
{
  "correctedQuery": "MATCH ...",
  "explanation": "The variable was propagated through WITH."
}
```

The correction must preserve the original intent and only fix syntax, scope, aggregation, property, or null-value issues.

### 9.4 Analytical Response

`AnalyticalResponseSchema` requires:

```json
{
  "answer": "Text based on actual results.",
  "followUpQuestions": [
    "Related question 1",
    "Related question 2"
  ]
}
```

The model must respond in the language of the question, not the language of the data.

It must also avoid inventing values, queries, or conclusions that are not supported by the received results.

## 10. Non-Functional Requirements

### Security

- Never allow the LLM to execute write operations.
- Reject queries containing `CREATE`, `MERGE`, `DELETE`, `SET`, `DROP`, `REMOVE`, or unauthorized `CALL` clauses.
- Prefer parameters over string interpolation.
- Do not expose credentials, internal prompts, or stack traces to the client.
- Validate question length and content.
- Limit execution time, the number of attempts, and the number of returned results.

### Reliability

- OpenRouter failures must produce explicit errors.
- Neo4j failures must not be converted into successful responses.
- Automatic correction must have a fixed limit, currently planned as one attempt.
- The state must preserve the original question and the query that failed.

### Observability

Log the following information without including sensitive data:

- Request identifier.
- Total execution time.
- LLM execution time.
- Neo4j execution time.
- Model used.
- Number of results.
- Number of corrections.
- Error type.

Never log API keys, complete email addresses, or unnecessary personal message content.

## 11. Local Setup

Prerequisites:

- Node.js version compatible with `package.json`.
- Docker and Docker Compose.
- OpenRouter API key.

Example `.env` file:

```env
OPENROUTER_API_KEY=sk-or-v1-...
OPENROUTER_MODELS=google/gemma-4-31b-it:free
```

Commands:

```bash
npm install
npm run docker:infra:up
npm run seed
npm start
```

Request:

```bash
curl -X POST http://localhost:4000/sales \
  -H 'Content-Type: application/json' \
  -d '{"question":"List all available courses"}'
```

To shut down the infrastructure:

```bash
npm run docker:infra:down
```

The `docker:infra:cleanup` script removes the volumes and the local storage directory. It should only be used when deleting the stored data is intentional.

## 12. Testing Strategy

### Recommended Unit Tests

- Extracting a question from a message.
- Empty questions or missing messages.
- Read-only query validation.
- Formatting structured responses.
- Handling empty results.
- Enforcing the correction attempt limit.
- Classifying simple versus complex questions using fixed LLM responses.

### Integration Tests

- Neo4j connection.
- Schema retrieval.
- `EXPLAIN` validation of valid queries.
- Execution of parameterized queries.
- Complete seed execution.

### End-to-End Tests

The scenarios in `tests/sales.e2e.test.ts` should verify:

- HTTP status codes.
- Presence of the `answer` field.
- Presence of the `followUpQuestions` field.
- Questions about courses, purchases, revenue, and progress.
- Handling of out-of-domain questions.
- LLM or Neo4j failures.

Ideally, tests should use a deterministic dataset. Tests against a real LLM should be separated from fast tests and have explicit cost and execution time limits.

## 14. Recommended Development Roadmap

### Phase 1 — Make the Minimum Workflow Functional

- Implement structured Cypher generation.
- Implement the executor using `validateQuery` and `query`.
- Implement structured analytical responses.
- Remove the `"hello world"` demonstration response.
- Create a test for "List all courses".

### Phase 2 — Security and Reliability

- Create a read-only query validator.
- Add execution time and result limits.
- Standardize error handling.
- Add correlated logs.
- Test Neo4j and OpenRouter unavailability.

### Phase 3 — Complex Questions

- Execute subquestions sequentially.
- Store each query and result in the state.
- Synthesize results using a dedicated prompt.
- Ensure that failures at any step are explicitly reported.

### Phase 4 — RAG and Semantic Caching

- Define what will be indexed: questions, answers, queries, or documents.
- Choose an embeddings model.
- Create a vector index in Neo4j.
- Define a similarity threshold.
- Invalidate the cache whenever the source data changes.
- Clearly distinguish semantic caching from graph queries.

### Phase 5 — Production

- Add authentication.
- Remove internal details from public responses.
- Implement metrics and tracing.
- Pin dependency versions and validate Node.js compatibility.
- Use appropriate data and secrets for each environment.
- Run deterministic tests in CI.

## 15. Reference Cypher Query Examples

List all courses:

```cypher
MATCH (c:Course)
RETURN c.name AS courseName, c.url AS url
ORDER BY c.name
```

Students who purchased a course:

```cypher
MATCH (s:Student)-[p:PURCHASED]->(c:Course)
WHERE c.name = $courseName AND p.status = 'paid'
RETURN s.name AS studentName, s.email AS email
ORDER BY s.name
```

Revenue per course:

```cypher
MATCH (s:Student)-[p:PURCHASED]->(c:Course)
WHERE p.status = 'paid'
RETURN c.name AS courseName, SUM(p.amount) AS revenue
ORDER BY revenue DESC
```

Students with completed courses:

```cypher
MATCH (s:Student)-[p:PROGRESS]->(c:Course)
WHERE p.progress = 100
RETURN s.name AS studentName, c.name AS courseName
ORDER BY s.name
```

These examples are read-only and should be used as a foundation for testing and evaluating the quality of queries generated by the LLM.

## 16. Glossary

- **Cypher**: The query language used by Neo4j.
- **Graph QA**: A question-answering approach that retrieves information by querying a knowledge graph.
- **LLM**: A Large Language Model used to interpret and generate text or code.
- **LangGraph**: A library for orchestrating stateful agent workflows.
- **RAG**: Retrieval-Augmented Generation.
- **Structured Output**: A model response validated against a schema, in this case using Zod.
- **Seed**: A process that populates the database with initial data.
- **Self-Correction**: An additional LLM call to fix an invalid query.
